## 质量检查五大维度

### 维度一：🔒 安全审计（使用 security-audit 技能）

按照 security-audit 技能的标准，检查：
- 代码中是否有密码、密钥等敏感信息泄露（重点检查 `.env` 是否被 git 跟踪、日志是否打印敏感信息）
- SQL 查询是否有注入漏洞（SQLAlchemy 是否全程参数化，有无拼接 SQL）
- 文件上传是否有路径遍历、类型绕过、大小限制缺失
- JWT 密钥管理是否规范、密码哈希是否正确（bcrypt）
- AI 特有风险：Prompt 注入（用户输入/文档内容是否可能操纵系统提示词）、SSRF（网页抓取类功能）
- 前端 XSS：`v-html` 渲染点（如 markdown 渲染）是否做了转义/白名单处理
- 依赖安全：`pip list --outdated`、`npm audit` 结果

### 维度二：📝 注释审查（使用 comments-check 技能）

按照 comments-check 技能的标准，检查：
- 注释覆盖率是否达标（30% 原则）
- 注释内容是否与代码实际逻辑匹配
- **关键设计点是否有"为什么这样设计"的注释**（面试项目最重要：FAQ 优先策略、SSE 选择、降级策略等必须有解释）

### 维度三：🛡️ 错误处理与健壮性

> 检查代码遇到意外情况时能否"优雅处理"，而不是直接崩溃。

检查清单：
- **try-catch 覆盖**：
  - 所有 LLM/embedding API 调用是否包裹异常处理（外部服务不可用是常态）
  - 所有文件读写、数据库操作是否有异常路径
- **降级策略**（本项目特色，重点检查）：
  - Redis 故障时限流是否降级放行（`redis_available()`）
  - FAQ 匹配失败是否降级走 RAG（不阻断对话）
  - LLM 失败是否返回友好错误（BusinessError 而非 500 堆栈）
- **后台任务健壮性**：
  - `process_document` 失败是否把状态置 failed 并记录原因
  - BackgroundTasks 中断后是否有重试兜底（文档重试接口）
- **空值/边界检查**：
  - 检索结果为空的处理（RAG 无结果时 LLM 是否会被约束"说不知道"）
  - 用户输入长度限制（Pydantic 校验）
- **错误信息质量**：
  - 用户可见的错误信息是否友好（❌ "Internal Server Error" → ✅ "大模型服务暂时不可用，请稍后重试"）
  - 是否区分"给开发者看的日志"和"给用户看的提示"

检查方法：
1. 搜索 `except` 统计外部调用（LLM/Redis/MySQL）的异常覆盖
2. 搜索 `raise BusinessError` 检查错误码使用是否规范
3. 逐服务检查降级路径是否真实存在（读代码验证，不是只看注释）

### 维度四：📐 代码规范与一致性

> 检查代码风格是否统一、命名是否清晰、分层是否合理。

检查清单：
- **分层规范**（本项目约定，重点检查）：
  - `api/` 只做参数接收与响应包装，业务逻辑必须在 `services/`
  - `models/`（ORM）与 `schemas/`（Pydantic）职责分离，不混用
  - `core/`（基础设施）不反向依赖业务模块
  - 向量库操作集中在 `rag/vectorstore.py`，不允许在 services 里直接 new Chroma
- **命名规范**：
  - Python 函数/变量 snake_case、类 PascalCase、常量 UPPER_SNAKE_CASE
  - 路由函数动词开头（create_/list_/update_/delete_），与 REST 语义一致
  - 命名是否"说人话"（❌ `fn1`、`data2` ✅ `retrieve_documents`、`chat_stream`）
- **响应规范**：
  - 所有接口统一 `{"code", "message", "data"}` 结构（用 `ok()` 包装）
  - 业务错误统一抛 `BusinessError` + `ErrorCode` 常量，不散落硬编码
- **Vue 前端**：
  - 组件职责单一，接口调用集中在 `src/api/index.js`
  - 是否滥用 `any`（JS 项目检查过度松散的类型）

检查方法：
1. 遍历 `backend/app/` 目录树，检查各层职责是否越界
2. 搜索 `import` 反向依赖（services 里 import api 等）
3. 搜索硬编码的错误码/响应结构

### 维度五：⚡ 性能与可维护性

> 检查代码中可能导致系统变慢或难以维护的地方。

检查清单：
- **数据库性能**：
  - 是否有 N+1 查询（列表接口逐条查统计应聚合查询）
  - 列表接口是否分页（对话记录等）
  - 索引使用是否合理（高频过滤字段是否建了索引）
- **AI 成本控制**（本项目特色）：
  - 多轮对话历史是否限量（CHAT_HISTORY_LIMIT）
  - FAQ 命中是否真的跳过了 LLM 调用
  - embedding 是否重复计算（同一文档重复向量化）
- **流式性能**：
  - SSE 生成器内是否持有数据库连接过久（生成器内自建 Session 是否正确关闭）
- **前端性能**：
  - 列表渲染是否用了 key、大列表是否分页
  - 轮询是否有停止条件（文档状态轮询在全部完成后应停止）
- **代码复杂度**：
  - 单个函数是否过长（超过 60 行建议拆分）
  - 是否有过深的嵌套（超过 3 层）
  - 是否有重复的代码块（DRY 原则）

检查方法：
1. 用 Grep 统计函数长度
2. 检查聊天/文档处理主流程的 Session 生命周期
3. 检查前端定时器的清理逻辑

## 工作流程

### 第一步：准备阶段

1. 确定审查范围：
   - 如果用户指定了文件 → 只审查指定文件
   - 如果用户说"全面检查" → 审查 `backend/app/` 与 `frontend/src/` 下所有代码
   - 如果用户说"增量检查" → 用 `git diff` 找出变更文件
2. 运行依赖检查：后端 `pip list --outdated`（backend 目录 .venv）、前端 `npm audit`（frontend 目录）

### 第二步：逐维度审查

按优先级依次审查五个维度：
1. 先做安全审计（最重要的，出问题最严重）
2. 再做注释审查（影响可读性）
3. 然后做错误处理检查
4. 接着做代码规范检查
5. 最后做性能检查

## 核心理念

1. **安全第一**：任何安全问题都是最高优先级，必须最先修复
2. **用数据说话**：注释覆盖率、错误处理率都要给出具体数字
3. **问题 + 方案**：不只挑毛病，每个问题都要给出可操作的修复方案
4. **循序渐进**：给出明确的修复顺序，让用户知道先修哪个
5. **面试导向**：审查报告指出的问题，同时说明"如果面试官问到这里，怎么回答"
6. **实事求是**：不夸大问题，不隐瞒风险

## 🚪 门禁模式（Gate Mode）

当调用方明确说「以门禁模式运行 / Gate Mode / 门禁检查」时，进入此模式。

### 与普通模式的区别

- 普通模式 = 五维度全面审查 + 完整报告
- 门禁模式 = 只做「快速但关键」的检查，回答一个问题：**现在能不能提交**

### 检查步骤（约 2~3 分钟）

1. **测试快速通过（必做）**：在 `backend/` 目录运行 `.venv/Scripts/python -m pytest tests/ -q`，全部通过才算过
2. **安全快速抽查（必做）**：`git diff --name-only` 拿到变更文件，用 Grep 扫这些文件里的硬编码敏感信息关键词（password、secret、token、apiKey、api_key、DASHSCOPE_API_KEY 等），逐条判断真伪
3. **注释快速抽查（从简）**：只抽查变更文件的注释与代码是否对得上，不要求完整覆盖率统计
4. 门禁模式**不跑 npm audit / pip outdated**（要联网、慢），留给普通模式

### 输出与判定

1. 回复的**最后一行必须严格是** `门禁判定: PASS` 或 `门禁判定: FAIL`
2. 判定写入 `.claude/gate/quality-report.json`（目录不存在先 `mkdir -p .claude/gate`），格式：

   ```json
   {"gate": "quality", "pass": true, "summary": "测试通过，未发现敏感信息", "checkedAt": "2026-08-31T10:00:00.000Z"}
   ```

3. FAIL 时按「先安全、后测试、最后注释」顺序列问题清单和修复方向
4. 门禁模式**只判定不改代码**（除非用户明确要求修复）
